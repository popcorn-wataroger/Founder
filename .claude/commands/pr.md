PR を作成する前の確認を、順番どおりに実行してください。

引数で Issue 番号が渡された場合はそれを使ってください（例: `/pr 43`）。
渡されていない場合は、ステップ3で特定します。

**重要なルール:**
- 1ステップでも失敗したら、そこで停止して「何が問題か」「どう直すか」を日本語で説明してください。次のステップに進んではいけません。
- 昇悟さんの確認が必要なステップでは、勝手に判断せず必ず質問してください。
- 各ステップの結果は日本語で報告してください。

---

## ステップ1: ブランチの確認

```bash
git branch --show-current
git status --short
```

**中止条件:**
- 現在のブランチが `main` の場合は、**ここで中止**してください。
  `main` への直接 push は禁止です。作業ブランチを切り直す必要があることを伝えてください。

**確認すること:**
- ブランチ名が `feature/` `fix/` `docs/` `refactor/` のいずれかで始まっているか
- ブランチ名に Issue 番号が入っているか（例: `feature/45-pr-command`）

命名規則から外れている場合は、そのまま進めてよいか昇悟さんに確認してください。

## ステップ2: コミット漏れと不要ファイルの確認

```bash
git status --short
git log origin/main..HEAD --oneline
```

**中止条件:**
- コミットされていない変更が残っている場合は、コミットするか確認してください。
- `.DS_Store` / `.env` / `.venv` / `*.key` / 認証情報ファイルが含まれていたら、**中止**してください。
  `.env` や APIキーの commit は絶対に避ける必要があります。

**確認すること:**
- `git log origin/main..HEAD` にコミットが1件以上あるか（0件ならPRを作れません）
- 意図しないファイルが混ざっていないか

## ステップ3: 対応する Issue の特定

引数で Issue 番号が渡されていればそれを使います。渡されていない場合は、
ブランチ名から番号を推測し、次のコマンドで実在するか確認してください。

```bash
gh issue view <Issue番号> --json number,title,state,body
```

**中止条件:**
- 対応する Issue が存在しない場合は、**中止**してください。
  「Issue を作らずに作業を始めない」がこのプロジェクトのルールです。
  Issue を先に作る必要があることを伝えてください。
- Issue がすでに CLOSED の場合は、そのまま進めてよいか確認してください。

**確認すること:**
- Issue の**完了条件を1つずつ読み上げ**、今回の変更で満たせているかを昇悟さんと確認してください。
- 満たせていない項目があれば、PRを出す前に対応するか、PR本文に「未対応」として明記するかを確認してください。

## ステップ4: ローカルCIチェック

`/ci` と同じ内容を順番に実行してください。

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy app/
GEMINI_API_KEY=dummy-key-for-ci APP_ENV=test uv run pytest -q --tb=short
```

**pytest にダミーのAPIキーを渡している理由:**
`app/vectorizer.py` は import された時点で Gemini のクライアントを作るため、
`GEMINI_API_KEY` が空だとテストの収集前に `ValueError: No API key was provided` で落ちます。
テストは実際のAPIを呼ばないのでダミー値で足ります（`.github/workflows/ci.yml` も同じ方法です）。

`.env` の `GEMINI_API_KEY` が空のまま作業している場合に必ず起きるので、
このエラーが出ても「テストが壊れている」わけではありません。

**中止条件:**
- 1つでも失敗したら、**中止**してエラー内容と直し方を説明してください。

## ステップ5: UI変更の確認

```bash
git diff origin/main...HEAD --name-only
```

`static/` 配下（`.html` / `.css` / `.js`）が変更されている場合のみ、このステップを実施します。
変更がなければスキップして構いません。

UI が変更されている場合は、次を昇悟さんに確認してください。

```bash
uv run uvicorn app.main:app --reload
```

- 社員画面（`EMP001` でログイン）を確認したか
- 管理者画面（`ADMIN` でログイン）を確認したか

**中止条件:**
- 両方の画面を確認できていない場合は、確認してもらってから先に進んでください。
  詳細な手順は `docs/ui-review.md` にあります。

## ステップ6: PR本文の作成

`.claude/CLAUDE.md` のテンプレートに沿って本文を作ってください。

```
Closes #番号

## 変更内容
- （何をしたか）

## 動作確認
- `uv run uvicorn app.main:app --reload` で起動
- EMP001 で社員画面を確認
- ADMIN で管理者画面を確認

## 相談事項
- （あれば）
```

**`Closes #番号` の書き方に注意してください。**

使えるキーワードは次の9つです（大文字小文字は問いません）。
`close` / `closes` / `closed` / `fix` / `fixes` / `fixed` / `resolve` / `resolves` / `resolved`

| 書き方 | 結果 |
|---|---|
| `Closes #43` | ✓ 正しい |
| `Fixes #43` / `Resolves #43` | ✓ 正しい（バグ修正なら `Fixes` が自然） |
| `Closes 43` | ✗ `#` がない |
| `#43` | ✗ キーワードがない（言及されるだけ） |
| `Closes #43, #44` | ✗ 2件目がリンクされない |
| `Closes #43, closes #44` | ✓ 複数Issueは1件ずつキーワードを書く |
| `Closes popcorn-wataroger/Founder#43` | ✓ 別リポジトリのIssueを閉じる場合の書き方 |

**ベースブランチが `main` でないと、キーワードは完全に無視されます。**
リンクも作られず、マージしても Issue は閉じません。PRは必ず `main` 宛にしてください。

**変更内容は、昇悟さんが自分の言葉で説明できる粒度で書いてください。**
専門用語をそのまま並べず、「何のために」「どう変わるか」がわかるようにします。

作成した本文を昇悟さんに見せて、**この内容でPRを作ってよいか確認**してください。
確認が取れるまでPRを作成してはいけません。

## ステップ7: PRの作成

確認が取れたら作成します。ベースブランチは必ず `main` です。

```bash
gh pr create --base main --title "<タイトル>" --body-file <本文ファイル>
```

## ステップ8: Closes リンクの検証（最重要）

**本文に書いただけでは、実際にリンクされたかどうかはわかりません。** 必ず検証してください。

```bash
gh pr view <PR番号> --json number,baseRefName,closingIssuesReferences \
  --jq '{pr:.number, base:.baseRefName, closes:[.closingIssuesReferences[].number]}'
```

**判定:**
- `closes` に対象の Issue 番号が入っていれば成功です。マージ時に Issue が自動で閉じます。
- `closes` が **空の場合は失敗**です。`Closes #番号` の書き方が間違っているか、本文に入っていません。
  ステップ6の表を見て本文を修正し、`gh pr edit <PR番号> --body-file <修正した本文>` で
  直してから、もう一度このステップを実行してください。
- `base` が `main` でない場合、マージしても Issue は閉じません。ベースブランチを直してください。

## 完了報告

全ステップが通ったら、次の形式で報告してください。

```
✓ PR作成完了

PR: #<番号> <タイトル>
リンク済みIssue: #<番号>（マージ時に自動でクローズされます）
CIチェック: 全通過
UI確認: 社員画面 / 管理者画面 ともに確認済み（UI変更がない場合は「対象外」）
```

そのうえで、**この PR の変更内容がアプリ全体で何の役割を持つか**を昇悟さんが
自分の言葉で説明できるか確認してください。説明できない場合は、できるまで解説してください。
