# 社内AIチャットボット — MVP要件定義書

## 1. プロダクト概要

NotebookLM的な社内ナレッジチャットボット。社長がアップロードしたソース（マニュアル、規定、社員個別資料など）をもとに、AIが社員の質問に回答する。

### コンセプト
- **社員向け：** LINE風チャットUIで社内ナレッジに即座にアクセス
- **社長向け：** ソース管理、チャットログ閲覧、スタッフ管理を一元化

---

## 2. ユーザーロールと認証

### ロール定義

ロールは4種類。値は `app/routers/auth_router.py` の定数に集約している。

| ロール | 対象 | アクセス範囲 |
|--------|------|-------------|
| `employee`（社員） | 全スタッフ | 社員用チャット画面（`#screen-chat`）。全社共通ソース＋自分の個別ソースでAIに質問、自分のチャットログ、自分の資料のアップロード、自分のパスワード変更 |
| `source_manager`（共通ソース管理者） | 共通資料の登録担当 | 社員ができることすべてに加え、共通ソース管理画面（`#screen-source-manager`）で全社共通ソースの登録・一覧・削除 |
| `ceo`（社長） | 1名 | 管理者画面（`#screen-admin`）。全ソース（共通・個別）の管理とダウンロード、全社員のチャットログと社員データの閲覧、ロールの変更 |
| `admin`（システム管理者） | アカウント管理担当 | アカウント管理画面（`#screen-account-admin`）のみ。アカウントの一覧・追加・パスワードの強制上書き・ロールの変更を行う |

**`admin` は業務データに一切アクセスできない。** チャットも、ソースの登録・閲覧も、社員データの閲覧もできない。`app/routers/auth_router.py` の `require_business_user()` が業務系APIで `admin` を403で弾き、ソース系・社員データ系のAPIは `require_ceo` / `require_source_uploader` のいずれにも `admin` を含めていない。社長（`ceo`）の「業務については全部見られる」とちょうど正反対の役割になる。

### 認証方式

- 社員マスタは **`users` テーブル**（Cloud SQL / PostgreSQL）。`data/users.csv` は**初期データ専用**で、起動時に `users` が空のときだけ投入する（`app/database.py` の `seed_users_if_empty()`）。運用中に追加したアカウントをCSVへ書き戻すことはしない
- ログイン画面で社員コード＋パスワード（`POST /api/login`）。認証に成功するとJWTを発行し、以降のAPIはこのトークンで判定する
- パスワードは **bcrypt のハッシュを `user_passwords` テーブル**に持つ。`users.password` は、まだハッシュが無い社員のログインに使うフォールバックで、そのログインが成功した時点でハッシュへ移行する（`app/routers/auth_router.py` の `verify_user_password()`）
- ロールは **`user_roles` テーブルの上書きを優先**し、上書きが無ければ `users.role` を使う（`app/users.py` の `resolve_role()`）。この「実効ロール」が4種類のいずれでもない場合は、ログインを拒否する
- ロールの変更は**対象者の次回ログインから有効**になる。ロールはログイン時に発行するJWTへ焼き付けられ、発行後は書き換えられないため

### 社員マスタの初期データCSV（`data/users.csv`）

起動時に `users` テーブルが空のときだけ読み込まれる、初期投入用のファイル。列は `users` テーブルの列と1対1で対応する。

```
user_id, employee_code, name, department, gender, birth_date, family, hire_date, employment_type, password, role, last_login_at
```

- `password` … 初期パスワード（平文）。初回ログイン時に `user_passwords` のハッシュへ移行する
- `role` … 初期ロール。運用中の変更は `user_roles` テーブルに記録され、そちらが優先される
- `last_login_at` … 空。実際の記録は `user_logins` テーブルが持つ

## 3. 画面構成

### 3-1. 社員用画面：LINE風チャットUI

#### 機能
- テキスト入力 → AIが全社共通ソースと自分の個別ソースをもとに回答
- チャット履歴はセッションごとに保持
- 自分の資料のアップロード（`POST /api/sources/my-upload`）。種別（個別）と持ち主はサーバーがJWTの user_id から決めるため、他人の資料としては登録できない
- 自分のパスワード変更（全画面共通のモーダル）
- レスポンシブ対応（スマホでも使える想定）

#### AI回答の参照範囲
- 全社共通ソース：○（参照可）
- 自分の個別ソース：○（実装済み）
- 他人の個別ソース：✕（絶対にアクセス不可）

絞り込みは `app/vector_store.py` の `search()` が行う。`ceo` 以外の検索では `scope='common'` に絞り、本人の user_id（`self_user_id`）が渡された場合だけ「自分の個別ソース」が範囲に加わる。`self_user_id` には必ずJWTから取り出した値を渡す（リクエスト由来の値を渡すと、他人の user_id を送るだけでその人の資料を読めてしまう）。

#### UI要件
- メッセージの吹き出し表示（自分＝右、AI＝左）
- 送信ボタン＋Enterキー送信
- ローディングインジケーター（AI応答待ち）
- チャット履歴のスクロール

---

### 3-2. 管理者画面（PC用）

3つのメインセクションで構成。

#### A. ソース管理

| 項目 | 内容 |
|------|------|
| アップロード対応形式 | PDF, Word(.docx), PowerPoint(.pptx), テキスト(.txt), ウェブURL |
| ソース種別 | 「全社共通」または「社員個別」を選択してアップロード |
| 社員個別の場合 | 対象社員を紐付け |
| 操作 | アップロード、削除、一覧表示 |
| 表示情報 | ファイル名、アップロード日時、種別、対象社員（個別の場合） |

#### B. チャットログ

| 項目 | 内容 |
|------|------|
| 一覧表示 | 日付、時刻、社員名、トーク内容（抜粋） |
| フィルター | 社員名、日付範囲 |
| 詳細表示 | クリックで該当チャット全文を閲覧可能 |

#### C. スタッフ一覧 → 社員データ画面

**スタッフ一覧：**
- カード形式で社員を一覧表示（アイコン＋名前）
- クリックで社員データ画面に遷移

**社員データ画面（詳細）：**

| セクション | 内容 | MVP対応 |
|-----------|------|---------|
| 基本情報 | 名前、社員コード、部署、性別、生年月日、家族構成、入社日、雇用形態 | ○ |
| 最終ログイン履歴 | 最終ログイン日時 | ○ |
| 「このスタッフについてチャット」ボタン | 押下でAIチャット開始（後述） | ○ |
| 最近のトーク内容 | 直近N件のチャットログをプレビュー表示 | ○ |
| トーク全文閲覧 | クリックで全チャット履歴を閲覧（ページスクロール可能） | ○ |
| 給与グラフ | 給与推移のグラフ表示 | ✕（将来対応） |
| 過去のソース | その社員に紐付いたソース一覧＋ダウンロード機能 | ○ |
| ソース追加 | その社員への個別ソースアップロード | ○ |

#### 「このスタッフについてチャット」機能

2つの用途を兼ねる：

1. **AIチャット（メイン）：** 社長がその社員について質問 → AIが共通ソース＋その社員の個別ソースを参照して回答
   - 例：「奥村さんの直近の評価は？」→ 個別ソース（評価資料）から回答
2. **ログ閲覧：** その社員とボットの過去のチャット履歴も参照可能

### 3-3. 共通ソース管理者の画面：共通ソース登録（`#screen-source-manager`）

`source_manager` でログインすると最初に開く画面。

| 項目 | 内容 |
|------|------|
| 対応形式 | PDF, Word(.docx), PowerPoint(.pptx), テキスト(.txt), ウェブURL |
| ソース種別 | 全社共通のみ（`scope='common'` 固定。個別ソースはこの画面から登録できない） |
| 操作 | アップロード（ドラッグ＆ドロップ／ファイル選択）、URL登録、一覧表示、削除 |
| 表示情報 | ファイル名、種別、登録日時 |

**管理者画面（3-2）と分けている理由：** 管理者画面はスタッフ一覧・社員データ・AIチャットモーダルが同居しており、初期化で `require_ceo` のAPIを呼ぶ。`source_manager` では403になるため、そのまま流用できない。「不要な部分を隠して見せる」形にすると隠し忘れがそのまま権限の穴になるので、共通ソースの登録だけができる専用画面に分けている。

**AIチャットも使える：** この画面と社員用チャット画面（3-1）は相互に行き来できる。`source_manager` は社員としての利用（共通ソース＋自分の個別ソースでの質問）もできる。

**削除の範囲：** 削除できるのは共通ソースだけ。個別ソース（他人の評価・給与など）には届かない。判定は `app/routers/sources_router.py` の `delete_source()` が行い、`ceo` 以外が `scope != 'common'` を指定した場合は403を返す。

---

### 3-4. アカウント管理画面（`#screen-account-admin`）

`admin` でログインすると開く画面。この画面が `admin` の唯一の画面で、チャットやソースの画面へは移動できない。

| 区画 | 内容 | API |
|------|------|-----|
| アカウント一覧 | 社員コード、氏名、ロール、ロールの変更日時、変更した人 | `GET /api/admin/accounts` |
| ロールの変更 | 一覧の行でロールを選び直して「変更」を押す | `PUT /api/admin/users/{user_id}/role` |
| アカウントの追加 | 社員コード、氏名、ロール、初期パスワードを入力して追加 | `POST /api/admin/accounts` |
| パスワードの強制上書き | 一覧から対象を選び、新しいパスワードを設定する | `PUT /api/admin/accounts/{user_id}/password` |

- 一覧には**全員が並ぶ**（社長・システム管理者も除外しない）。除外すると、その2人のパスワードだけ画面から復旧できなくなるため
- **自分自身のロールは変更できない**（サーバーが403を返し、画面でも操作できない状態にする）。自分を降格させると、権限を戻す手段がDBの直接操作しか無くなるため
- ロールの変更は対象者の次回ログインから有効になる旨を、一覧のそばに常時表示する

## 4. データモデル（概念設計）

### テーブル構成

```
users（社員マスタ）
├── user_id（PK）
├── employee_code（社員コード）
├── name
├── department（部署）
├── gender（性別）
├── birth_date（生年月日）
├── family（家族構成）
├── hire_date（入社日）
├── employment_type（雇用形態）
├── password（初期パスワード。CSVからの投入時のみ使う平文）
├── role（employee / source_manager / ceo / admin ＝ 初期ロール）
└── last_login_at（未使用。実際の記録は user_logins が持つ）

sources（ソース）
├── source_id（PK）
├── file_name
├── file_type（pdf / docx / pptx / txt / url）
├── file_path（ストレージパス or URL）
├── scope（common / individual）
├── owner_user_id（FK → users, NULLなら全社共通）
├── uploaded_at
└── uploaded_by（FK → users）

chat_sessions（チャットセッション）
├── session_id（PK）
├── user_id（FK → users）
├── started_at
└── context_type（general / staff_inquiry）
     ※ staff_inquiry = 社長が「このスタッフについてチャット」で開始

chat_messages（チャットメッセージ）
├── message_id（PK）
├── session_id（FK → chat_sessions）
├── role（user / assistant）
├── content
├── created_at
└── referenced_sources[]（参照したソースIDリスト）

user_logins（最終ログイン日時）
├── user_id（PK, FK → users）
└── last_login_at（UTC・ISO形式の文字列）

user_roles（ロールの上書き）
├── user_id（PK, FK → users）
├── role（employee / source_manager / ceo / admin）
├── updated_at（変更日時）
└── updated_by（変更した人の user_id）

user_passwords（パスワード）
├── user_id（PK, FK → users）
├── password_hash（bcrypt）
└── updated_at
```

**運用中に変わる値を users から分けている理由：** `users` は `data/users.csv` から一度だけ投入される社員マスタで、滅多に変わらない。最終ログイン・ロール・パスワードは運用中に変わるため、1社員1行の別テーブルに持つ。こうしておくと、

- ロールは「誰がいつ変えたか」（`updated_at` / `updated_by`）を一緒に残せる。`users.role` を直接書き換える形だと、この記録が残らない
- パスワードは平文の初期値（`users.password`）とハッシュ（`user_passwords.password_hash`）が別の場所に分かれ、移行が済んだかどうかを行の有無で判断できる

実効ロールの決め方は `app/users.py` の `resolve_role()` に集約している（`user_roles` の上書きがあればそれ、無ければ `users.role`）。

### 権限マトリクス

**この表は実装（`app/` 配下）を正とする。** `CLAUDE.md` の権限ルール表と同じ内容を保つこと。

| 操作 | employee | source_manager | ceo | admin |
|------|------|------|------|------|
| AIチャットの利用 | ○ | ○ | ○ | ✕ |
| 共通ソースでAIに質問 | ○ | ○ | ○ | ✕ |
| 自分の個別ソースでAIに質問 | ○ | ○ | ○ | ✕ |
| 他人の個別ソースでAIに質問 | ✕ | ✕ | ○ | ✕ |
| 全社共通ソースの登録（ファイル / URL） | ✕ | ○ | ○ | ✕ |
| 自分の個別ソースの登録 | ○ | ○ | ○ | ✕ |
| 他人の個別ソースの登録 | ✕ | ✕ | ○ | ✕ |
| 全社共通ソースの削除 | ✕ | ○ | ○ | ✕ |
| 個別ソースの削除（自分の分を含む） | ✕ | ✕ | ○ | ✕ |
| ソースのダウンロード | ✕ | ✕ | ○ | ✕ |
| 全ソース一覧の閲覧 | ✕ | ✕ | ○ | ✕ |
| 共通ソース一覧の閲覧 | ✕ | ○ | ○ | ✕ |
| 社員別のソース一覧の閲覧 | ✕ | ✕ | ○ | ✕ |
| チャットログの閲覧 | 自分のみ | 自分のみ | 全員分 | ✕ |
| 社員データの閲覧 | ✕ | ✕ | ○ | ✕ |
| アカウント一覧の閲覧 | ✕ | ✕ | ✕ | ○ |
| アカウントの追加 | ✕ | ✕ | ✕ | ○ |
| 他人のパスワードの強制上書き | ✕ | ✕ | ✕ | ○ |
| 自分のパスワードの変更 | ○ | ○ | ○ | ○ |
| ロールの変更 | ✕ | ✕ | ○ | ○ |

判定を書いている場所（増やさず、ここに集約する）:

| 判定 | 場所 |
|------|------|
| 共通ソースを登録・削除してよい役割か | `app/routers/auth_router.py` の `can_upload_common_source()` |
| アカウントを管理してよい役割か | `app/routers/auth_router.py` の `can_manage_accounts()` |
| ロールを変更してよい役割か | `app/routers/auth_router.py` の `can_change_user_role()` |
| 業務機能を使ってよいか（`admin` を締め出す） | `app/routers/auth_router.py` の `require_business_user()` |
| 個別ソースを登録してよいか（種別ごとの判定） | `app/routers/sources_router.py` の `check_scope_permission()` |
| 個別ソースを削除してよいか | `app/routers/sources_router.py` の `delete_source()` |
| AIの検索範囲（他人の個別ソースの除外） | `app/vector_store.py` の `search()` |

補足:

- **ロールの変更**は `ceo` と `admin` の両方ができる。ただし**自分自身は対象にできない**（どちらのロールでも403）。アカウントの一覧・追加・パスワードの強制上書きは `admin` だけができる
- **社員データの閲覧**の対象からは `ceo` と `admin` を除外する（`STAFF_LIST_EXCLUDED_ROLES`）。スタッフ一覧は業務上の社員を並べる画面で、業務データを持たない `admin` は開く中身が無いため
- **チャットログ**は、自分の分は全員（`admin` を除く）が見られ、他人の分は `ceo` だけが見られる

## 5. 非機能要件

### セキュリティ
- チャットボット利用規約に「業務用チャットのログは管理目的で記録されます」と明記
- 初回ログイン時に同意チェック
- 個別ソースの権限制御（社員が他人のデータにアクセスできないこと）

### 想定規模
- 社員数：100人以下
- 同時接続：数十人程度

### 技術スタック

| 領域 | 採用技術 | 備考 |
|------|---------|------|
| フロントエンド | HTML / CSS / JavaScript | フレームワークなし、バニラ構成 |
| バックエンド | Python（FastAPI） | 非同期対応。Gemini API の呼び出しも非同期で扱う |
| AI基盤 | Gemini API | 回答生成 `gemini-flash-latest` / ベクトル化 `gemini-embedding-001` |
| ベクトルDB | Qdrant | 軽量・セットアップ容易・OSSで無料利用可 |
| ファイルストレージ | Google Cloud Storage (GCS) | ソースファイルの保管 |
| ホスティング | Google Cloud Platform (GCP) | Cloud Run + Cloud SQL 等 |
| チャット履歴保持期間 | 無期限 | 削除は手動対応 |
| リポジトリ | `Founder` | GitHub |

※ ベクトルDBは Qdrant を推奨。理由：Docker一発で起動可能、REST APIがシンプル、Python SDKが充実、GCP上でも Cloud Run でホスト可能。pgvector（PostgreSQL拡張）も候補だが、Cloud SQL と同居させる場合はセットアップがやや複雑。

### 技術的前提
- Webアプリケーション（LINE風、ネイティブアプリではない）
- 外部システム連携：MVPでは不要
- 社員マスタ：`users` テーブル（Cloud SQL）。`data/users.csv` は初期投入用のダミーデータで、起動時に `users` が空のときだけ読み込む（2章を参照）

## 6. フェーズ計画

### Phase 1（MVP）— 本ドキュメントのスコープ
- 社員用LINE風チャットUI（3-1）。自分の資料のアップロードを含む
- 管理者画面（3-2。ソース管理、ログ閲覧、スタッフ一覧・詳細）
- 共通ソース管理者の画面（3-3。全社共通ソースの登録・一覧・削除）
- アカウント管理画面（3-4。アカウントの一覧・追加、ロールの変更）
- AIチャットエンジン（権限ベースのソース参照。共通ソース＋自分の個別ソース）
- 社員コード＋パスワードによる認証（社員マスタは `users` テーブル。`data/users.csv` は初期投入のみ）
- パスワード管理（本人による変更 `PUT /api/me/password` と、システム管理者による強制上書き `PUT /api/admin/accounts/{user_id}/password`。保存は bcrypt のハッシュ）
- 「このスタッフについてチャット」

### Phase 2（拡張）
- 給与グラフ表示
- 本人への個別データ公開（自分の評価・給与を自分で閲覧）
- 検索・フィルター強化

### Phase 3（発展）
- Google Workspace / Slack連携
- 通知機能
- 分析ダッシュボード（よくある質問の傾向など）
